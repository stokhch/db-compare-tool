# DB Compare — сравнение и копирование Oracle / PostgreSQL

Локальное веб-приложение (Node.js + Express, Vue 3 + DevExtreme) для:

- **сравнения схем**: Oracle ↔ Oracle, PostgreSQL ↔ PostgreSQL, Oracle ↔ PostgreSQL;
- **сравнения данных** построчно по ключу, с отчётом о расхождениях;
- **копирования баз** между машинами: перелив по соединениям (любые направления), `pg_dump`/`pg_restore`, Oracle Data Pump по сети, запуск **ora2pg**.

## Что взято из готовых проектов

| Идея | Откуда |
|---|---|
| Отчёт «объекты и количество строк с обеих сторон» (таблицы, индексы, PK/FK, последовательности, триггеры, представления, функции) | `ora2pg -t TEST` |
| Нормализация значений перед сравнением (числа, даты до микросекунд, UTC, CHAR, `''`/NULL), хранение истории сравнений | CrunchyData **pgCompare** |
| Потоковое сравнение без выгрузки таблиц в память, сравнение отсортированных по ключу потоков | **reladiff** / data-diff |
| Сравнение таблиц без ключа как мультимножеств строк | Google **DVT** (row hash) |
| Маппинг типов Oracle → PostgreSQL (NUMBER(p,0) → smallint/integer/bigint, DATE → timestamp(0), CLOB → text …) | **ora2pg** |
| Функции пакетов Oracle ищутся как `пакет_функция` (plsql2pg) и `пакет.функция` (ora2pg PACKAGE_AS_SCHEMA) | **plsql2pg**, **ora2pg** |
| Проверка кода PL/pgSQL расширением plpgsql_check в транзакции с откатом | **plsql2pg** (checker.py) |
| Допуск при сравнении чисел (абсолютный / относительный) | **plsql2pg** (verify.py) |
| Понятные подсказки к ошибкам подключения | **plsql2pg** (checker.py), расширено для Oracle |
| ora2pg из комплекта plsql2pg для Windows (Perl + ora2pg без установки) | **plsql2pg** |

ora2pg не переписан, а подключён как внешняя утилита: приложение собирает `ora2pg.conf` из сохранённых подключений и показывает результат.

## Установка (Windows)

1. Установите **Node.js 18+** (https://nodejs.org).
2. Распакуйте архив и запустите `start.bat`. При первом запуске ставятся зависимости и собирается интерфейс, затем открывается http://localhost:3700.

Вручную:
```bat
npm run setup     :: зависимости сервера и клиента + сборка интерфейса
npm start         :: http://localhost:3700
```
Порт меняется переменной `PORT`. По умолчанию сервер слушает только `127.0.0.1`. Чтобы открыть доступ из сети, задайте `HOST=0.0.0.0`, но учтите, что авторизации в приложении нет.

### Необязательные утилиты

| Нужно для | Что установить |
|---|---|
| Oracle 11g или старые парольные верификаторы | Oracle Instant Client. Путь к нему укажите в *Настройках* (включится Thick-режим). Oracle 12.1+ работает без клиента. |
| pg_dump / pg_restore | Клиент PostgreSQL той же или более новой версии, чем сервер. На Windows ищется автоматически в `C:\Program Files\PostgreSQL\*\bin`. |
| ora2pg | Проще всего — распакованный [plsql2pg-windows-x64.zip](https://github.com/stokhch/plsql2pg/releases/tag/windows-latest): в нём уже есть Perl и ora2pg. Укажите его папку в *Настройках* (по умолчанию проверяется `C:\plsql2pg`). Для действий с подключением к Oracle Perl нужен ещё драйвер `DBD::Oracle` — его наличие видно в *Настройках*. Либо своя установка: Strawberry Perl + `DBD::Oracle` + `DBD::Pg` + ora2pg. |
| Проверка кода PostgreSQL | Расширение [plpgsql_check](https://github.com/okbob/plpgsql_check) на сервере PostgreSQL. Подключать его к базе не обязательно: на время проверки оно создаётся в транзакции с откатом (нужны права на CREATE EXTENSION). |
| Data Pump | Ничего ставить не нужно: импорт запускается PL/SQL-пакетом `DBMS_DATAPUMP` на сервере-приёмнике. |

### DevExtreme
Без лицензионного ключа DevExtreme 25.x показывает баннер «For evaluation purposes only». Ключ вашей компании положите в `client/.env` (`VITE_DEVEXTREME_LICENSE=…`, образец лежит в `client/.env.example`) и пересоберите интерфейс командой `npm run build`.

## Как пользоваться

Подробная инструкция со скриншотами и схемами: [docs/guide.html](docs/guide.html). В приложении она открывается пунктом меню «Инструкция» (адрес `/guide`).


1. **Подключения**: добавьте базы. Для Oracle можно указать service name, SID или полную строку (EZConnect или TNS-дескриптор). Пароли хранятся в `data/connections.json` в зашифрованном виде (AES-256-GCM). Ключ лежит в `data/.secret`, его можно задать переменной `DBCOMPARE_SECRET`.
2. **Сравнение схем**: выберите источник и приёмник со схемами и нажмите «Сравнить». Для баз PostgreSQL код функций, процедур и триггеров дополнительно проверяется через plpgsql_check: это аналог INVALID-объектов Oracle, который показывает, например, ссылки на несуществующие колонки. Результат группируется по категориям, кликом по категории включается фильтр. Отчёт можно открыть в HTML и отправить коллегам.
   - **Выбранные объекты**: переключатель «выбранные объекты» показывает список объектов схемы. Его можно отфильтровать по подстроке в имени, а кнопкой «Добавить связанные» дополнить выбор зависимостями: от чего зависят выбранные объекты (родительские таблицы по FK, таблицы представлений и кода, функции триггеров, последовательности), что зависит от них, или и то и другое, в том числе рекурсивно. Зависимости берутся из словаря: в Oracle из `ALL_DEPENDENCIES` и ограничений, в PostgreSQL из `pg_depend`, ограничений и триггеров, а зависимости кода PostgreSQL ищутся по тексту функций.
   - **Скрипт синхронизации структуры**, как «Schema Compare → migrate» в DBeaver. Он генерирует операторы, которые приводят приёмник к источнику: создание таблиц, добавление колонок, смену типов, NOT NULL, ключи, индексы и последовательности. Для одинаковых СУБД добавляется ещё DDL представлений, функций, пакетов и триггеров (`pg_get_*def` / `DBMS_METADATA`). У каждого оператора указан уровень риска. Удаление лишних объектов по умолчанию выключено. Нужные операторы можно отметить, скачать как `.sql`, скопировать или выполнить на приёмнике. В PostgreSQL выполнение идёт в одной транзакции и откатывается при ошибке.
3. **Сравнение данных**: загрузите список общих таблиц, при необходимости выберите нужные, задайте ключ и условие WHERE. В результате по каждой таблице видно, сколько строк отсутствует, сколько лишних и сколько отличается. Примеры отличий показаны с точностью до колонки. Кнопка «Добавить связанные таблицы» добавляет к выбору родительские и (или) дочерние таблицы по FK.
   - **Скрипт синхронизации данных** генерирует INSERT для отсутствующих строк, UPDATE только для отличающихся колонок и, по желанию, DELETE для лишних строк. Скрипт строится потоком во время повторного сравнения, поэтому подходит и для больших таблиц. Порядок учитывает внешние ключи: вставки идут от родительских таблиц к дочерним, удаления — в обратном порядке. Литералы формируются под диалект приёмника (TO_DATE, TO_TIMESTAMP, HEXTORAW, TO_CLOB, bytea и т. д.). Скрипт можно скачать или сразу выполнить: в PostgreSQL в одной транзакции, в Oracle с фиксацией пачками по 1000 операторов. В таблицах без ключа лишние строки скриптом не удаляются. BLOB больше 2000 байт в Oracle не помещаются в литерал, для них используйте перелив.
4. **Копирование**: на вкладке выберите способ.
   - *Перелив таблиц*: Oracle⇄PG в любую сторону. Отсутствующие таблицы создаются с маппингом типов, данные загружаются в порядке FK, на время загрузки можно отключить FK, после загрузки выравниваются последовательности. Код (PL/SQL) этим способом не переносится.
   - *pg_dump / pg_restore*: дамп и восстановление, только дамп или восстановление из сохранённого файла. Дампы лежат в `data/dumps`, их можно скачать.
   - *Oracle Data Pump*: сетевой импорт через DB link (аналог `impdp NETWORK_LINK`) с переименованием схемы. Кнопка «Команды expdp/impdp» генерирует команды для варианта через файлы.
   - *ora2pg*: SHOW_REPORT (оценка миграции), выгрузка DDL и кода, COPY, а также проверки TEST / TEST_COUNT / TEST_DATA.
5. **Задачи**: история всех запусков с журналом, отчётами и экспортом в JSON. Долгие задачи можно отменить.

## Миграция и проверка результата

| Раздел | Что делает |
|---|---|
| **Профиль данных** | Проверяет фактические значения колонок до выбора типов: дробные числа в «целых» колонках, время в DATE (можно ли `date`), `NUMBER` без точности с целыми значениями (`integer`/`bigint` вместо `numeric`), символ `\0` (PostgreSQL его не примет), пустые строки (`''` в Oracle = NULL), LONG, максимальные длины. С указанным приёмником проверяет и его фактические типы: переполнение, округление, потерю времени, усечение строк. |
| **Миграция → Конвейер** | Перенос одной кнопкой для репетиций: структура (таблицы без ключей) → данные в N потоков → PK, уникальные ключи, индексы, FK → последовательности → ANALYZE / DBMS_STATS → проверка (число строк, агрегаты или построчно). Время каждого шага и оценка окна простоя. Прерванный запуск можно продолжить: уже загруженные таблицы пропускаются. |
| **Миграция → Догрузка изменений** | Перед переключением переносит только изменения: по колонке даты изменения (вставка или обновление: `INSERT … ON CONFLICT` / `MERGE`) или по росту числового ключа. Удалённые строки находит сравнением одних ключей. |
| **Миграция → Права и окружение** | Из Oracle собирает роли и права (`GRANT`), комментарии, синонимы (→ представления или `search_path`), DB links (→ шаблоны `oracle_fdw`/`postgres_fdw`), задания `DBMS_SCHEDULER` (→ `pg_cron`, расписание переводится в cron). Операторы можно отметить, скачать или выполнить. |
| **Проверки → Сравнение запросов** | Один набор запросов выполняется в обеих базах. Сравниваются результаты (как наборы строк, по ключу или по порядку) и время. Медленные в PostgreSQL запросы отмечаются и получают `EXPLAIN`. Можно добавить все общие представления и топ запросов из `V$SQL` / `pg_stat_statements`. Наборы запросов сохраняются. |
| **Проверки → Сверка расчётов** | Шаги расчёта (`BEGIN pkg.proc; END;` / `CALL pkg_proc()`) выполняются в обеих базах, итоговые таблицы сравниваются в тех же сессиях, затем обе транзакции откатываются. CSV-файлы не нужны. **Шаблон по процедурам раздела**: выбираете процедуры Oracle по порядку (например, `maket_pt.del_pt`, `maket_pt.ras_pt`). Приложение само строит вызовы для обеих баз: аргументы берутся из `ALL_ARGUMENTS`, даты — из фильтра периода, OUT-параметры выводятся через `DBMS_OUTPUT`. Имена в PostgreSQL ищутся как `пакет_процедура` и `пакет.процедура`. Итоговые таблицы (`*_rab`, `*_arch`, протоколы) предлагаются из `ALL_DEPENDENCIES`. Ответы процедур (OUT-параметры) тоже сравниваются. Вместо отката можно фиксировать изменения: тогда перед расчётом в каждой базе выполняется очистка периода, а после сравнения — шаги «после». |
| **Проверки → Готовность данных** | Перед сверкой расчёта считает, есть ли за период исходные данные в обеих базах: справочники с условием (`tr_pok` с `kodrazd = 46`), суточные `sv_*`, архивы соседних расчётов. Можно включить автоматический список всех таблиц, к которым применим фильтр периода. «Пусто в обеих» объясняет, почему расчёт дал пустой результат без ошибок. Списки сохраняются. |
| **Проверки → Юнит-тесты функций** | Метод plsql2pg, но без скриптов SQL*Plus и файлов. Каждая функция пакета вызывается в обеих базах: сначала базовый вызов, затем по очереди меняется один параметр (0, −1, дроби, 29 февраля, конец года, кириллица, NULL…), не более 60 вызовов. Каждый вызов выполняется в точке сохранения с откатом. Ответ Oracle — эталон. Одинаковые ошибки считаются совпадением (`NO_DATA_FOUND` = `P0002`, деление на ноль = `22012`, `-20001` = `45001`). Набор с ответами Oracle можно сохранить и повторять без Oracle, в том числе из регламента. |
| **Миграция → Зависимости пакетов** | Перед переносом пакета проверяет, всё ли, что он вызывает, уже есть в PostgreSQL. Источники зависимостей: `ALL_DEPENDENCIES` и вызовы `ПАКЕТ.процедура` в тексте. Проверяются собственные подпрограммы, процедуры других пакетов, таблицы, представления и последовательности. Показывает, каких пакетов не хватает, порядок установки и циклы. |
| **Фильтр периода и пользователя** | Общий для «Сравнения данных» и «Проверок» (запоминается). Применяется к таблицам, где есть нужные колонки: `d_beg`/`d_end` (точное совпадение или пересечение с периодом), суточные даты (`sv_date`), `prognoz = 0` («только факт»), `u_m` (текущий пользователь — `USER` в Oracle и `upper(current_user)` в PostgreSQL — или заданные значения). Названия колонок настраиваются. |
| **Проверки → Сверка по агрегатам** | Для больших таблиц: COUNT, SUM/MIN/MAX чисел, диапазоны дат, суммарные длины строк и LOB — по таблице или по месяцам/годам. Затем построчно сравниваются только разошедшиеся группы. |
| **Импорт дампа** | Импорт файла expdp или exp, когда к базе-источнику не подключиться. Работает в два шага: сначала анализ, потом импорт по плану (подробности ниже). |
| **Код приложения** | Сканирует папку проекта (.js/.ts/.vue/.java/.cs/.py/.sql, XML-маппинги). Находит Oracle-конструкции в SQL-строках (NVL, DECODE, ROWNUM, `(+)`, CONNECT BY, `seq.NEXTVAL`, `:параметры` → `$1`, `MINUS`, `LISTAGG`, `''`/NULL…) и вызовы node-oracledb (`execute`, `executeMany`, OUT-параметры, `autoCommit`, `rowsAffected`, колонки ЗАГЛАВНЫМИ). Предлагает замену. Если указать базу Oracle, находит вызовы `пакет.процедура` и предлагает `пакет_процедура` (plsql2pg). Результат можно выгрузить в CSV. |
| **Регламент** | Наборы проверок на период параллельной работы. Проверка добавляется кнопкой «В регламент» на любом экране сравнения. Набор запускается вручную, по расписанию cron (пока приложение запущено) или командой `node server/cli.js suite "Имя"` из Планировщика заданий Windows (код возврата 0/1/2). Итог сравнивается с прошлым запуском, при расхождениях отправляется webhook (Teams, Slack, Mattermost). |

## Импорт дампа Oracle

**Анализ.**
- По заголовку файла определяется формат (Data Pump или старый exp), версия, кодировка, режим экспорта и части набора `exp_01.dmp`, `exp_02.dmp`…
- Архив `.gz` распаковывается.
- Если сервер базы не видит файл, приложение создаёт каталог Oracle на папку с дампом. Если и это не помогает (база на другом компьютере или в контейнере), файл копируется в `DATA_PUMP_DIR` через соединение с базой.
- Состав дампа читается через `DBMS_DATAPUMP` (`SQL_FILE`): схемы и объекты, табличные пространства, роли и получатели прав, DB links, задания, ссылки на схемы вне дампа, колонки `VARCHAR2(n BYTE)`. Для exp состав берётся из DDL прямо в файле.
- Состояние приёмника проверяется по пунктам:
  - версия и кодировка;
  - контейнер: подключение к `CDB$ROOT` вместо PDB считается ошибкой;
  - права;
  - существующие схемы: число объектов и подключённые сеансы;
  - табличные пространства и свободное место;
  - роли;
  - оставшиеся задания Data Pump от прерванных запусков.
- Зависимости кода: тексты пакетов, процедур, функций, триггеров, типов и представлений из дампа разбираются, и ссылки на другие схемы, пакеты, таблицы, последовательности и DB links сверяются с дампом и с базой-приёмником (`ALL_USERS`, `ALL_OBJECTS`, синонимы, `ALL_DB_LINKS`). Чего нет ни там, ни там — показывается до импорта со списком объектов, которые станут невалидными (ORA-04063, PLS-00201). Встроенные пакеты (`DBMS_*`, `UTL_*` и т. п.), комментарии и строки не учитываются. Разбор текстовый: динамический SQL (`EXECUTE IMMEDIATE '…'`) не проверяется.

**Решения.** Для каждой проблемы предлагается исправление:
- Схема уже есть и не пуста — нужно выбрать действие:
  - удалить схему (с завершением сеансов);
  - импортировать под другим именем;
  - `REPLACE`, `TRUNCATE` или `APPEND` для таблиц;
  - пропустить схему.
- Нет табличного пространства — `REMAP_TABLESPACE` в существующее или создание нового.
- Нет пользователя, а в дампе нет `CREATE USER` — пользователь создаётся с квотами и правами.
- Недостающие роли создаются.
- Кодировка меняется с однобайтовой на UTF-8 — импорт в два этапа: структура, затем перевод колонок `BYTE → CHAR`, затем данные. Так не будет ORA-12899.
- DB links и задания можно не импортировать.
- Мастер-таблицы прерванных заданий удаляются.
- При переименовании схемы с типами применяется `TRANSFORM=OID:N`.

**План.** Перед запуском показываются SQL подготовки и эквивалентные команды `impdp`. Необратимые действия требуют подтверждения.

**Результат.**
- Ошибки из журнала сгруппированы по кодам, к каждой даны объяснение и подсказка. Безвредные (ORA-31684 и др.) скрыты.
- Показываются:
  - строки по таблицам;
  - невалидные объекты после перекомпиляции, с текстом ошибок;
  - объекты, которых в базе меньше, чем в дампе.
- Кнопка «Применить исправления и повторить анализ» включает исправления, найденные по ошибкам.

Старый формат exp импортируется утилитой `imp` полной установки Oracle (путь задаётся в «Настройках»). `NLS_LANG` выставляется по кодировке дампа.

## Работа с базой

| Раздел | Что делает |
|---|---|
| **Браузер объектов** | Объекты схемы по типам с фильтром. Таблица открывается с вкладками: данные (постранично, с условием WHERE, сортировкой и правкой строк по первичному ключу; изменения сохраняются одной транзакцией, а если затронута не одна строка — откатываются), колонки с комментариями, ограничения, индексы (размер и число обращений), триггеры, зависимости в обе стороны (двойной щелчок открывает связанный объект), DDL (`DBMS_METADATA` в Oracle, собранный из словаря в PostgreSQL), статистика. Представления — запрос и данные. Пакеты, процедуры и функции — код с номерами строк, ошибки компиляции (в PostgreSQL через plpgsql_check) с подсветкой строк, параметры. Действия: перекомпилировать, собрать статистику / `ANALYZE` / `VACUUM`, обновить материализованное представление, открыть в SQL-консоли. |
| **SQL-консоль** | Запрос к одной базе или к двум сразу: результаты показываются рядом с подсветкой отличий (по ключевым колонкам или как наборы строк). По умолчанию режим «только чтение»: всё выполняется в транзакции с откатом. Есть дерево таблиц и колонок, история запросов, выгрузка в CSV, кнопка «План выполнения». Скрипты исправлений из других разделов открываются здесь одной кнопкой. |
| **Производительность → Сравнение планов** | Запросы выполняются в обеих базах. Время и планы показываются рядом; для Oracle — `DBMS_XPLAN` с фактической статистикой, если есть права. По плану PostgreSQL приложение находит проблемы и даёт готовый SQL исправления: полное чтение с отбрасыванием большинства строк (нужен индекс), приведение типа колонки (после миграции `integer` ⇄ `numeric` мешает индексу), функцию над колонкой (нужен индекс по выражению), неточную оценку строк (`ANALYZE`), сортировку и хеширование на диске (`work_mem`), вложенный цикл по таблице без индекса, долгую JIT-компиляцию. Запросы можно взять из сохранённого набора или из самых тяжёлых в источнике. |
| **Производительность → Индексы** | Внешние ключи без индекса, дубли и индексы, покрытые другими, неиспользуемые и недействительные индексы, таблицы без первичного ключа, частое полное чтение. Если указать вторую базу, показываются индексы, потерянные при миграции, с готовым `CREATE INDEX`. |
| **Производительность → Активность** | Сеансы, долгие запросы и `idle in transaction`. Видно, кто кого блокирует; корень цепочки подсвечивается. Можно отменить запрос или завершить сеанс. Список обновляется каждые 5 секунд. |
| **Аудит здоровья** | Оценка из 100. Проверяются: раздутые таблицы, устаревшая статистика, последовательности и `integer`-ключи у предела, возраст транзакций (wraparound), заполнение табличных пространств, невалидные объекты, отключённые триггеры и ограничения, `UNLOGGED`-таблицы, подключения, кэш. Ищутся «сироты»: строки, ссылающиеся на несуществующие записи, там, где связь есть по смыслу, а внешнего ключа нет. Если нарушений нет, предлагается добавить внешний ключ. Скрипт исправлений собирается одной кнопкой. |
| **Поиск по базе** | Значение во всех таблицах, текст в коде (процедуры, пакеты, представления, триггеры, проверки, задания) или имена таблиц и колонок. |
| **История схемы** | Снимки структуры: вручную или по расписанию, новый снимок появляется только при изменениях. Можно сравнить два снимка или снимок с текущим состоянием. Журнал DDL (кто, когда, какой командой) ставится одной кнопкой: событийный триггер в PostgreSQL, триггер `AFTER DDL ON SCHEMA` в Oracle. |
| **Документация** | HTML (печатается в PDF) и Markdown: таблицы и колонки с комментариями, ключи, связи, индексы, проверки, представления, подпрограммы и ER-диаграмма. Отдельно подсчитано, сколько таблиц и колонок без описания. |
| **Тестовая копия** | **Срез:** от выбранной таблицы с условием берутся дочерние строки на нужную глубину и всё, на что они ссылаются; справочники копируются целиком. Внешние ключи в копии не нарушаются. **Маскирование:** персональные данные находятся по именам колонок и по значениям. Замены детерминированные, поэтому связи сохраняются. Фамилии, имена и отчества подбираются с учётом рода; СНИЛС и ИНН получают правильные контрольные суммы; телефоны, паспорта и карты сохраняют формат; даты сдвигаются на ±180 дней. |
| **Резервные копии** | PostgreSQL — `pg_dump`, Oracle — экспорт Data Pump на сервер базы. Проверка: чтение оглавления или заголовка; для PostgreSQL — пробное восстановление во временную базу. Старые копии удаляются (ротация). По расписанию — через «Регламент», там же уведомление о неудаче. |

Аудит, индексы, планы, резервные копии и снимки схемы можно добавить в «Регламент».

## Проверка перед запуском и разбор ошибок

Перед запуском операций, где чаще всего что-то ломается, приложение проверяет обе базы и параметры. Найденные проблемы показываются карточками с вариантами исправления, как в импорте дампа. Выбранные исправления применяются при запуске: меняются параметры задачи или выполняется SQL до и после неё. Необратимые действия требуют подтверждения.

| Операция | Что проверяется и что исправляется |
|---|---|
| **Перелив таблиц, конвейер миграции** | Схема-приёмник (создать). Права на схему и таблицы (готовый `GRANT`). Отсутствующие таблицы (создать). Непустые таблицы: очистить, пропустить или добавить. Колонки, которых нет в приёмнике (добавить). Колонки уже, чем в источнике (расширить). Несовместимые типы. `GENERATED ALWAYS` (переключить на `BY DEFAULT`). serial / identity (после загрузки сдвинуть последовательности на `MAX`). Триггеры (отключить на время загрузки). Невыбранные родительские таблицы (добавить). Внешние ключи при параллельной загрузке. Права суперпользователя для отключения FK. Последовательности. BFILE. Кодировка. Объём. |
| **pg_dump / pg_restore** | Версии pg_dump и pg_restore относительно серверов: предлагается установленный клиент нужной версии. Место на диске. Нет базы-приёмника: создать с кодировкой и локалью источника. Непустая база: `--clean`, пересоздать базу или восстановить поверх, с завершением подключений. Отсутствующие расширения и расширения, которые может создать только суперпользователь. Роли-владельцы и получатели прав (`--no-owner`, `--no-privileges` или создать роли). Табличные пространства (`--no-tablespaces`). Число потоков. |
| **Data Pump по сети** | Пробный DB link с сервера-приёмника к источнику, с объяснением ORA-12541 / 12514 / 01017 и ловушки «localhost». `CDB$ROOT`. Права на обеих сторонах. Существующая схема: удалить, переименовать, `REPLACE`, `TRUNCATE` или `SKIP`. Табличные пространства (`REMAP` или создать). Роли. Смена кодировки (импорт в два этапа с переводом колонок в CHAR). LONG. DB links и задания. Остатки прерванных заданий. Место. |
| **ora2pg** | ora2pg, DBD::Oracle, DBD::Pg (можно переключиться на комплект plsql2pg). Подключение и объекты схемы. Схема и таблицы в PostgreSQL, непустые таблицы (`TRUNCATE_TABLE`). Параллельность. |
| **Догрузка изменений** | Колонка даты изменения: существует ли, есть ли индекс (готовый `CREATE INDEX … ONLINE`), есть ли NULL. Ключи в источнике. Ключ для upsert в приёмнике (создать PK). Режим «по ключу» для строковых ключей. Удаления. Слишком давнее или будущее «с какого момента». |
| **Сравнение данных** | Таблицы без ключа: ищется колонка с уникальными значениями и предлагается как ключ. Большие таблицы. Плавающая точка (допуск). Пустые строки как NULL. |

После любой задачи с ошибками под её журналом появляется блок «Что пошло не так». Ошибки Oracle и PostgreSQL, вывод pg_restore и ora2pg сгруппированы, к каждой группе есть подсказка. Кнопка «Повторить с исправлениями» запускает задачу заново:
- с изменёнными параметрами: очистка таблиц, отключение FK, `--no-owner`, `--clean`, два этапа для Data Pump и т. п.;
- с продолжением с места остановки, если загрузка оборвалась;
- через повторную проверку перед запуском, если исправление требует пересчёта (например, расширения колонок).

## Как сравниваются данные

- Обе выборки сортируются по ключу (PK, затем уникальный ключ, затем ключ, заданный вручную) и сравниваются потоком методом merge-join. Память не зависит от размера таблицы.
- Строковые ключи сортируются бинарно: в PostgreSQL через `COLLATE "C"`, в Oracle через `NLS_SORT=BINARY`. Если порядок в базах всё же различается (другая кодировка базы, разные типы ключа), приложение само переходит в режим хеш-таблицы: приёмник загружается в память.
- Нормализация значений:
  - числа приводятся к каноническому десятичному виду (`1.50` = `1.5`);
  - `boolean` сравнивается с `NUMBER(1)` как 1/0;
  - даты и время приводятся к `YYYY-MM-DD HH:MI:SS.ffffff` в UTC, Oracle DATE совпадает с `timestamp(0)`;
  - у CHAR обрезаются хвостовые пробелы;
  - пустая строка приравнивается к NULL (по умолчанию для пары Oracle⇄PG);
  - JSON сравнивается без учёта порядка ключей и пробелов, BLOB/bytea — по MD5.
- Допуск для чисел (как в plsql2pg verify): значения равны, если |a−b| ≤ абсолютного допуска или ≤ относительного × max(|a|,|b|). Строки, совпавшие только с учётом допуска, считаются отдельно («в допуске»). Для таблиц без ключа допуск не применяется.
- Таблица без ключа сравнивается как мультимножество хешей строк.

## Ограничения и что проверено

- **Проверено на живом PostgreSQL 16**: сравнение схем, сравнение данных во всех трёх режимах, перелив PG→PG с созданием таблиц (копия совпала с исходной на 100%), pg_dump/pg_restore. Логика нормализации и маппинга типов покрыта юнит-тестами: `node test/unit.test.js`.
- **Oracle-часть на реальном Oracle не запускалась**, потому что в среде разработки его не было. Это относится и к импорту дампа, а также к Oracle-части новых разделов: планам `DBMS_XPLAN`, аудиту, активности, экспорту резервных копий и журналу DDL. Разбор заголовков, DDL, план и разбор журнала покрыты юнит-тестами, но реальные вызовы `DBMS_DATAPUMP`, `UTL_FILE` и `imp` нужно проверить на первом запуске (лучше на небольшом дампе). Это касается и шаблона расчёта, юнит-тестов функций, проверки зависимостей и вывода OUT-параметров через `DBMS_OUTPUT`. Их логика (генерация вызовов, соответствие кодов ошибок, разбор зависимостей) покрыта юнит-тестами, а сторона PostgreSQL проверена вживую. Сюда входят чтение метаданных, сравнение и перелив с участием Oracle, Data Pump. SQL написан для Oracle 12c+ по представлениям `ALL_*`. Первый запуск на Oracle сделайте на тестовой схеме.
- Сравнение схем Oracle⇄PG проверяет состав объектов и совместимость типов. Тексты процедур и CHECK-ограничений не сравниваются, потому что синтаксис в этих СУБД разный: для CHECK сравнивается их количество.
- **Проверка перевода кода Oracle → PostgreSQL** (в «Сравнении схем», флажок «Проверить перевод кода»). Ищет функции, которые могли быть переведены неправильно, по трём группам признаков:
  - **Сигнатура.** Совпадает ли число входных параметров, совместимы ли типы параметров и результата. Совпадают ли OUT-параметры, вид объекта (функция или процедура) и имена параметров; от имён зависят вызовы `p => …`.
  - **Остатки Oracle в тексте PostgreSQL.** `NVL`, `DECODE`, `SYSDATE`, `ROWNUM`, `(+)`, `seq.NEXTVAL`, `EXECUTE IMMEDIATE`, `SQL%ROWCOUNT`, `DUP_VAL_ON_INDEX`, `VARCHAR2` и т. п. Если такие функции есть в базе (orafce или собственные обёртки), это не считается ошибкой.
  - **Смысловые ловушки.** Сравнение с `''` (в Oracle это NULL). `SELECT … INTO` без `STRICT` при обработчике `NO_DATA_FOUND`. `TRUNC` от даты, `TO_NUMBER` без формата, `COMMIT` в функции, `WHEN OTHERS THEN NULL`.
  - **Логика относительно оригинала из `ALL_SOURCE`.** Сверяются таблицы, которые код изменяет, число `IF` и циклов, исчезнувшие `RAISE_APPLICATION_ERROR`, `COMMIT`. Слишком короткий текст или заглушка тоже отмечаются.

  Проверки эвристические: каждая находка содержит строку и фрагмент кода и означает «посмотрите сюда», а не «ошибка точно есть». Тело пакета делится на подпрограммы по заголовкам из спецификации, поэтому приватные процедуры пакета засчитываются соседней.
- Сравнение схем дополнительно сверяет состав колонок представлений и материализованных представлений. Если у представления не хватает колонок, в скрипт синхронизации попадает комментарий о том, что его нужно пересоздать.
- Колонки INTERVAL при кросс-СУБД сравнении могут показываться как разные из-за формата.
- Перелив не переносит индексы (кроме PK), FK, CHECK, DEFAULT и код. Для полной миграции структуры используйте ora2pg (TABLE, VIEW, PACKAGE…) или Data Pump / pg_dump.
- В Data Pump по сети не переносятся таблицы с LONG / LONG RAW (ограничение Oracle).
- `session_replication_role = replica` (отключение FK в PostgreSQL) требует прав суперпользователя. Без них загрузка идёт в порядке зависимостей.

## Структура

```
server/
  index.js            REST API + раздача интерфейса
  db/                 адаптеры Oracle (node-oracledb) и PostgreSQL (pg)
  meta/               чтение метаданных в единую модель
  compare/schema.js   сравнение схем
  compare/data.js     сравнение данных (merge / map / multiset)
  copy/transfer.js    перелив таблиц
  copy/pgdump.js      pg_dump / pg_restore
  copy/datapump.js    Oracle Data Pump (DBMS_DATAPUMP, NETWORK_LINK)
  copy/ora2pg.js      обёртка ora2pg
  lib/                нормализация, маппинг типов, задачи, хранилище, отчёты
client/               Vue 3 + DevExtreme (Vite)
data/                 подключения, настройки, история задач, дампы (создаётся автоматически)
```

Режим разработки: `npm run dev` (сервер) и `npm --prefix client run dev` (интерфейс на :5173 с проксированием /api).
